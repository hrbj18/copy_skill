# 单次开发指导文档：双任务科技内容工作台

日期：2026-08-26

## 一、开发目标

把现有“抖音采集与单视频素材处理工具”升级为一个可长期使用、资源受控、界面可随时关闭的本地工作台。本次只交付两个明确任务：

1. 每日新闻：由 Windows 独立计划任务在北京时间 02:00 汇总上一自然日 00:00–23:59 的高价值科技新闻，在 03:00 前形成固定 Markdown 和机器可读 JSON。新闻事实必须来自可追溯新闻源；抖音只用于发现与衡量关注度。
2. 灵感发现：白天一键执行，整次最多参考 100 条抖音视频元数据；完成去重、聚类和排序后，只允许少量高价值视频进入下载、转写、OCR 和模型分析，输出可直接供后续创作使用的灵感卡片。

工作台仅负责开关、任务启动、参数和状态，不暴露 Cookie、密钥、关键词、模型、并发、转写等实现细节。关闭工作台不得终止已经启动的后台任务。

## 二、冻结的产品与工程决策

- 不修改 `D:\codex_work\OpenMontage`，只在本项目生成稳定输出和集成快照。
- 不修改 `third_party/MediaCrawler`；搜索时间范围、总量预算和持久浏览器适配全部放在项目自有代码中。
- 不依赖“可回溯昨日 12 次抖音榜单”这一未经保证的能力。每日新闻以新闻源发现为主，抖音搜索/现有采集结果为热度佐证；未来若获得官方历史榜权限，再作为增强源接入。
- 新闻入选门槛是“一手/官方来源至少一个，或两个相互独立的可靠来源”。不满足门槛的内容只能列入待核验，不得伪装成已确认新闻。
- 每日新闻严格使用北京时间目标自然日；发布时间不明或越界的来源不能成为当日确认新闻。
- 灵感任务的“100 条”是整次任务的去重后元数据预算，不是每关键词 100 条，更不是下载 100 个视频。
- 灵感任务最多深读 20 条元数据、最多处理 5 个媒体文件，默认处理 3 个；视频和音频默认是临时文件，转写/OCR/摘要完成后删除。
- 每个任务使用互斥锁、原子状态文件和独立子进程；重复点击或计划任务重叠不得并发执行同一任务。
- 中转站只承担结构化提炼和文案生成；连接失败时保留确定性降级输出，不丢失采集结果，不泄露 API Key。
- 关机状态无法在 02:00 执行。计划任务启用 `WakeToRun` 与 `StartWhenAvailable`：电脑睡眠时尝试唤醒，错过时间则在下次可运行时补跑；需要 Windows 用户保持登录态以复用抖音浏览器会话。

## 三、任务拆分

### 任务 1：配置、状态和数据契约

- 新增 `jobs.daily_news`、`jobs.inspiration`、`workbench` 配置并验证上限。
- 新增原子运行状态、任务锁、控制状态和最近输出索引。
- 固定每日新闻、灵感报告的 Markdown 字段与对应 JSON 结构。

### 任务 2：每日新闻核心

- 实现 RSS/Atom/JSON 新闻源适配器，支持 HTTPS 和本地夹具。
- 按北京时间解析发布时间并严格筛选昨日自然日。
- 对相似事件去重聚类，保留所有来源；执行来源可靠性门控。
- 使用抖音元数据匹配事件关键词并生成“关注度信号”，明确其不是事实证据。
- 生成新闻三要素：时间、主体/地点、事件，并附新闻价值、抖音热度、权威来源、待核验、创作角度。
- 没有合格来源时生成诚实的空报告/待核验区，不编造内容。

### 任务 3：灵感发现核心

- 将搜索词压缩为受控查询组，并对 MediaCrawler 结果执行全局预算截断。
- 标准化、去重、题材聚类和价值排序，最多保留 100 条参考元数据。
- 仅对前 20 条进行详细候选分析，默认最多 3 条、硬上限 5 条进入现有临时媒体管线。
- 汇总为 5–10 张灵感卡：推荐度、一句话灵感、有趣之处、内容骨架、参考素材与时间戳、待核验、推荐标题。
- 若浏览器登录失效或媒体处理失败，任务标记为 `partial`/`needs_login`，仍保存已完成结果。

### 任务 4：后台执行和 Windows 调度

- 增加统一 worker 命令，支持 `daily-news`、`inspiration` 和确定性离线输入。
- 后台任务使用项目虚拟环境启动，与 Tkinter 界面生命周期解耦。
- 生成并安装当前用户的 Windows 计划任务：每天 02:00、错过补跑、唤醒、禁止重复实例、失败重试。
- 提供安装、查询、立即运行和卸载命令；计划任务 XML 不包含密钥或 Cookie。

### 任务 5：轻量工作台

- Tkinter 单窗口：每日任务开关、下次运行时间、参考视频数（默认 100）、一键灵感、刷新、打开最新输出。
- 状态只展示：最后/下次运行、当前阶段、候选/深读/媒体处理数、抖音登录、中转站、新闻源、错误摘要、临时目录大小。
- 界面关闭前若任务仍在运行，只提示“后台继续”，不停止任务。
- 提供根目录双击启动脚本。

### 任务 6：文档与兼容性

- 更新项目 Skill 的操作说明和配置参考，使其能调用新命令，但本次先保证正常项目功能完整。
- 保留现有 CLI 与 26 项基线测试行为。
- 完成验收后，只向 `docs/项目开发过程文档.md` 追加本次记录，绝不读取或重写旧内容。

## 四、开发流程

1. 先建立状态/锁和固定报告渲染器，以测试冻结数据契约。
2. 实现新闻源抓取、日期边界、事件聚类、来源门控、抖音热度匹配和新闻报告。
3. 实现全局预算搜索与灵感候选管线，复用现有临时媒体处理能力。
4. 将两条管线接入 CLI worker，补齐失败降级、状态与日志。
5. 实现计划任务 XML/管理命令，再实现只依赖状态文件的 Tkinter 工作台。
6. 更新配置、启动入口和 Skill 文档。
7. 先跑单元/集成测试，再做本机真实环境冒烟测试和计划任务安装；检查输出、锁、磁盘、密钥安全。
8. 对照验收标准修复全部阻断问题，最后追加项目开发过程记录。

## 五、安全和范围边界

- API Key 只从被忽略的 `.env.local`/环境变量读取，不写入配置、日志、状态、测试夹具、Markdown 或计划任务 XML。
- Cookie 与浏览器用户目录不复制、不导出、不展示。
- 对抖音请求设置查询数、结果数、并发和重试上限，不进行高频或无界抓取。
- 永久保留正文、来源链接、结构化元数据、转写缓存；默认不长期保留 MP4/WAV/关键帧。
- 任何网络或模型失败都必须有限时、可结束、可重跑，不允许无限重试。
- 不把抖音标题、字幕、点赞量或模型推断作为新闻事实。

## 六、验收标准

### A. 数据与报告

1. 给定跨时区新闻夹具，目标日报告只包含北京时间该自然日的合格事件；边界前后内容均被排除。
2. 同一事件的多来源文章被合并，来源门控正确：有官方源或两个独立可靠源才可进入确认新闻；单一非官方源只进待核验。
3. 每条确认新闻 Markdown 都包含“推荐级别、时间、主体/地点、事件、新闻价值、抖音热度、权威来源、待核验、创作角度”。
4. 每张灵感卡都包含“推荐度、一句话灵感、有趣之处、内容骨架、参考素材、待核验、推荐标题”。
5. 没有合格数据时仍生成格式完整、明确说明原因的报告，不产生虚构新闻或虚构时间戳。

### B. 规模、性能与存储

1. 灵感任务配置为 100 时，去重后参考元数据不超过 100，详细候选不超过 20，媒体处理不超过 5；自动化测试必须验证三个上限。
2. MediaCrawler 命令的总预算可证明受控，不能出现“每个关键词各抓 100 条”的放大效应。
3. 默认完整媒体处理结束后，临时 MP4/WAV/关键帧全部删除；缓存和输出仍可用于断点续跑。
4. 临时目录受 2 GiB 配额和 24 小时 TTL 约束；任务结束状态记录剩余字节数。

### C. 后台与工作台

1. 相同任务并发启动时只有一个获得锁，另一个可读地退出；异常退出后的陈旧锁可以安全恢复。
2. 关闭工作台不终止已启动 worker；状态文件能持续显示阶段、计数、完成时间、输出路径和简短错误。
3. 工作台默认参考数为 100，输入被限制在安全范围；界面不显示密钥、Cookie 或高级采集参数。
4. Windows 计划任务查询成功，触发时间为每天 02:00，启用错过补跑、唤醒和防重入；任务动作只指向本项目虚拟环境和 CLI。

### D. 真实依赖与回归

1. 全部既有测试和新增测试通过。
2. `doctor` 通过；`llm-doctor` 能连接已配置的 `gpt-5.6-luna`，且任何输出不含 API Key。
3. 至少一个真实 HTTPS 新闻源完成获取冒烟测试；若外部源当天无内容，只要求连接、解析和错误处理正确。
4. 使用小规模抖音搜索或已有真实采集数据完成一次灵感报告冒烟测试，不为了验收下载大量视频。
5. 扫描项目受版本控制范围与生成的任务 XML，确认没有 Cookie/API Key 明文；不扫描或读取被明确禁止的过程文档内容。
6. 未修改 `D:\codex_work\OpenMontage` 和 `third_party/MediaCrawler`。

## 七、明确不在本次范围

- 不实现或承诺抖音历史 12 次榜单的追溯接口。
- 不构建复杂的素材审核、账号管理、关键词编辑或视频编辑界面。
- 不让工作台常驻 24 小时，也不承诺电脑完全关机时执行。
- 不直接向 OpenMontage 写入文件或修改其定时任务。
- 不进行 Skill 瘦身或移除完整开源依赖；待正常项目功能长期验证后再做封装优化。
