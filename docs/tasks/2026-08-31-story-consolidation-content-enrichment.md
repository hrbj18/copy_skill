## 1. 背景与已确认缺陷

当前 V2 能收集目标日抖音公开视频元数据、计算热度并发布不可变候选包，但 2026-08-30 冻结数据证明现有标题二元词重叠聚类同时存在误合并和漏合并：

- “小米自研芯片/汽车/AI”与“阿里、智谱大模型价格战”因泛词及搜索关键词发生跨事件误合并；
- “9 月 15 日 V27 开源”与“腾讯混元 Hy4 Preview”发生跨产品误合并；
- 《无限大》定档、试玩、Reaction 等围绕同一新闻事件的视频仍散落为多行；
- 多视频聚类一律标记高置信度，不能解释为什么合并，也没有记录相关但不同事件；
- `story_id` 取决于最高互动代表标题，互动变化会导致同一故事 ID 漂移；
- 候选包主要保存标题和热度，长发布文案偶有出现但不系统，高热视频没有按预算补取画面文字或转写，也没有形成事件级摘要。

抖音材料继续只作为选题发现、内容样本和公开热度证据。本任务不核验新闻真伪，也不允许模型、图片或人工偏好改变热度排名。

## 2. 开发目标

1. 将 V2 的输出单位从“标题相似的视频簇”升级为可解释、稳定的“新闻事件故事”。
2. 高精度合并同一事件，明确保留同事件下的定档、实测、观点、参数解读等内容角度；宁可把不确定项保留为相关故事，也不得凭泛词强行合并。
3. 为每个故事生成不依赖最高互动代表视频的稳定 `story_id` 和结构化事件指纹。
4. 先利用平台发布文案；对排名靠前且文字不足的代表视频，在总预算内选择性执行画面 OCR，并仅在 OCR 仍不足时有限回退本地 ASR。
5. 使用现有 OpenAI-compatible 模型对已提取文字做一次受控的批量归纳，生成标题、摘要、要点、内容角度和待核验主张；模型失败时必须发布确定性降级摘要。
6. OP 顶层榜单一行只展示一个故事，所有贡献视频、别名、内容角度和证据嵌套保留；热度、账号矩阵、Top 3 图片、不可变发布和同日非退化合同不得回归。

## 3. 核心设计

### 3.1 三类关系

任意两个视频或故事只能得到以下关系之一：

- `same_story`：共同指向同一主体、同一产品/版本及兼容动作，可合并；
- `related_topic`：共享公司、领域或大类，但产品、版本、动作不足以证明是同一事件，只建立关联不合并；
- `different_story`：存在互斥主体、产品/版本或明显不同事件，不得合并。

关系必须带理由、置信度和命中的正向/负向锚点。搜索关键词只保留为发现 provenance，严禁参与事件身份或聚类相似度。

### 3.2 事件指纹

每条视频从标题/发布文案提取并保存：

- 规范化文本和信息词；
- 非泛化话题标签、书名号产品名、英文/数字型号、品牌/主体锚点；
- 动作标签，如发布、开源、定档、上线、升级、实测、回应；
- 日期、版本和数值标识，仅用于区分与待核验提示，不作为事实确认。

强命名锚点冲突优先于普通词重叠。聚类不得把新视频词集合不断并入后再与后续视频比较；加入现有簇时必须同时通过冻结主锚点和成员冲突检查，阻断链式漂移。

### 3.3 稳定故事 ID 与代表视频

- `story_id` 由业务日期和事件指纹的稳定主体材料计算，与输入顺序、互动数和代表视频选择无关。
- 代表视频仍按原始有效互动优先，用于深挖内容和展示，不参与 ID 生成。
- 同一运营矩阵内继续只让最高互动视频贡献有效热度，但其他视频完整保留。
- 第二代表视频只在第一条文字明显不足、内容角度互补或存在冲突时选择；同一 source group 默认最多深挖一条。

### 3.4 内容提取优先级

1. 原始平台发布文案、字幕或描述；
2. 对文字不足的高热代表视频做画面 OCR；
3. OCR 仍不足且预算允许时，最多对少量视频做本地 ASR；
4. 无临时媒体地址、外部失败或预算耗尽时保留标题级降级结果，不阻止整包发布。

临时媒体地址只允许在采集清洗前进入进程内索引，不能写入 JSON、Markdown、日志、缓存或不可变包。原始文件仍须执行现有敏感字段清洗。

### 3.5 模型边界

- 模型只归纳输入中已有的标题、发布文案、OCR/ASR 文本，不联网、不核真、不补事实；
- 模型输出不能新增输入中不存在的数字；故事 ID 必须与输入逐项匹配；
- 模型结果、模型是否成功、真伪字段、图片和人工偏好均不得改变热度分数及顺序；
- 模型按批次调用，设置有限超时和最多一次生成；失败时逐故事使用确定性摘句摘要；
- 所有数字、日期、价格、规格、性能和公司表态继续进入 `claims_to_verify`。

## 4. 预算冻结

整个每日流程继续受 `max_wall_seconds=3600` 约束。新增内容阶段采用独立子预算：

- 最多为热度前 10 个故事生成详细摘要；其余故事保留标题级结构化摘要；
- 最多深挖 12 条代表视频，其中媒体下载/OCR 最多 6 条；
- 第二代表视频最多 2 条，只用于证据不足或互补角度；
- OCR 总预算不超过 6 分钟，单视频不超过 60 秒；
- ASR 最多 2 条，总预算不超过 3 分钟，单条子进程有限超时；
- 模型最多 2 个批次，每批最多 8 个故事，单次遵守既有 120 秒超时且不重试；
- 新增阶段一旦子预算或全局预算耗尽，立即降级并继续生成合法 partial 包。

图片仍只处理热度 Top 3；本任务不增加图片数量、图片网络请求或关键词规模。

## 5. 具体任务拆分

### 任务 A：事件指纹与关系分类

1. 新增项目自有故事聚类模块，隔离确定性规范化、锚点提取、关系判定和故事 ID。
2. 将现有 V2 聚类切换为高精度关系聚类，移除搜索关键词参与身份的旧逻辑。
3. 输出 `event_signature`、`clustering_decisions`、`related_story_ids`、关系理由和置信度。
4. 保持矩阵有效互动、账号覆盖、热度公式和稳定排序的原有语义。

### 任务 B：代表视频与安全原始内容索引

1. 为账号采集和关键词采集增加清洗前只读回调；无论回调成功与否都必须执行清洗。
2. 只在内存保存内容字段与临时媒体地址，按 video ID 关联；发布前验证输出中没有临时地址或敏感字段。
3. 实现代表视频/补充视频的确定性选择及可解释选择理由。

### 任务 C：受控内容深挖

1. 复用现有 `visual_ocr.py` 的画面抽帧/OCR预算和临时目录清理。
2. OCR 不足时使用既有独立 ASR 子进程，严格限制调用数与超时。
3. 为每个故事输出 `content_evidence`、`extraction_status`、`extraction_methods`、质量与降级原因，绝不持久化媒体 URL。

### 任务 D：事件级归纳与 OP 合同

1. 先生成确定性摘要，再对预算内故事做模型批量归纳和数字越界校验。
2. 输出 `canonical_title`、`event_summary`、`key_points`、`content_angles`、`claims_to_verify`、`representative_video`、`supporting_videos`。
3. Markdown 顶层一行一个故事，贡献视频、相关故事和提取证据折叠为子项。
4. 升级 V2 contract 版本，同时保持 `candidates`/`stories` 兼容别名、不可变 READY/manifest/current/latest 和非退化发布。

### 任务 E：验证、修复与交接

1. 用 2026-08-30 冻结数据回放已知误合并/漏合并样本。
2. 运行聚焦测试、完整 pytest、compile、CLI、handoff audit 和敏感字段扫描。
3. 在外部条件允许时执行一个有界真实内容采集 smoke；若登录、平台、临时媒体或模型阻塞，只能报告 live partial，不得把回放测试冒充真实成功。
4. 更新当前 handoff，并仅通过追加脚本写入一次开发过程记录。

## 9. 完成标准

只有以下条件均有证据时，代码实现可标记完成：

1. 已知误合并与漏合并回归样本全部通过，并有关系理由。
2. 故事 ID 对输入顺序、互动变化和代表切换稳定。
3. 高热视频按预算获得比短标题更丰富的内容证据；无法获取时有明确降级原因。
4. OP 看到的是事件级故事榜，而不是重复视频列表；全部视频、热度和账号矩阵 provenance 仍完整。
5. 模型只整理、不核真、不增事实、不改排名，失败不阻断发布。
6. 全流程在一小时总预算内有确定性停止和 partial 发布路径。
7. 聚焦测试、完整 pytest、compile、CLI surface、handoff audit、敏感扫描和边界检查通过。
8. 真实 smoke 如实分级；外部证明缺失时最终结论必须明确为 live partial。
9. `third_party/MediaCrawler`、OpenMontage、历史包、凭据、计划任务和全局预算边界均未被破坏。
