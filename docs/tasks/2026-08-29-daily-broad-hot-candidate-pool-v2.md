# 单次开发指导文档：昨日完整热点候选池 V2

日期：2026-08-29  
状态：当前任务合同  
工作目录：`D:\work\copy_skill`

## 1. 背景与问题定义

现有“每日素材交换”已经证明了不可变版本包、READY 标记、哈希清单、按日期消费和 Top 素材图交接等基础设施，但当前正常入口仍读取固定的 2026-08-28 选择文件，只发布 5 条经过事实与图片门槛筛选的新闻；真实抖音搜索也只有 `AI新品` 一个关键词，配置上限为 10 条元数据。

这不符合新的产品职责。`copy_skill` 在本阶段是“昨日抖音科技热点发现与素材供给器”，不是事实核查器，也不是 OpenMontage 的最终编辑。它必须尽量完整地保留昨日发现的高热新闻候选，让 OP 自行选择；不得因为未经证实、尚未找到官方来源、没有图片或编辑判断不成熟而删除热点。只有排序后的 Top 3 需要获取图片，以控制耗时。

## 2. 本次开发目标

实现一条可重复运行的“昨日完整热点候选池 V2”生产链：

1. 以北京时间自然日为边界，采集所有已启用、已批准的对标账号和可信新闻账号在目标日期发布的视频元数据。
2. 同时执行多关键词、有限预算的抖音搜索，覆盖科技快讯、AI、大模型、开源项目、芯片、机器人、智能硬件、系统更新和游戏新品。
3. 合并两条来源通道，先按视频去重，再按新闻事件聚类；保留事件下全部贡献视频、账号、链接、发布时间和互动数据。
4. 仅依据公开互动数据、新鲜度、跨账号/跨来源覆盖进行可解释排序，不使用事实真伪、图片状态或大模型主观判断改变名次。
5. 发布尽可能宽的候选池供 OP 选择；只为最终 Top 3 尝试获取图片。
6. 从启动到交换包发布设置 3600 秒硬上限，并提供各阶段耗时、截止原因和部分成果。
7. 延续现有不可变交换包、原子指针、READY、manifest/hash、按日期消费和中文工作台入口。

## 3. 不可妥协的产品规则

### 3.1 职责边界

- 抖音视频只证明“某内容在抖音出现及其公开热度”，不能作为新闻事实证据。
- 本任务不得联网核验新闻真实性，不得以事实来源数量作为候选入池、排序或发布成功条件。
- 每个候选及总简报必须显著标注：`copy_skill 未核验真实性，候选仅供 OP 选题与后续核验。`
- `confirmed_facts`、`evidence_status` 等旧字段可以为了兼容继续存在，但必须为 `not_checked` 或空，且不能参与过滤、排序和状态判定。
- 无图、仅一条视频、传闻、未证实、标题不完整的候选仍须保留；只记录相应状态和风险提示。
- 不替 OP 决定最终选题，不生成最终播报稿，不写入 OpenMontage，不调用 RunningHub 或付费视频生产。

### 3.2 日期边界

- `business_date` 是 Asia/Shanghai 的目标自然日，范围严格为当日 `00:00:00 <= published_at < 次日 00:00:00`。
- 工作台默认目标为当前北京时间的“昨天”，同时允许显式传入日期用于补跑和验收。
- 无可靠发布时间的记录不得混入目标日期候选池，但应计入排除统计并说明原因。

### 3.3 来源边界

- 账号通道：采集配置中 `enabled=true` 且已正式批准的 benchmark/trusted 账号。`candidate` 生命周期账号在得到明确晋升前仍不进入生产采集。
- 搜索通道：执行本合同规定的受控关键词，不得在互联网漫无目的扩展。
- 不得修改 `third_party/MediaCrawler`；项目适配必须位于 `src/`、`config/` 或 `skills/`。
- 不得读取、输出或提交 Cookie、浏览器配置、API 密钥或 `.env.local` 内容。

## 4. 采集策略

### 4.1 账号通道

- 对所有已启用、已批准账号执行目标日采集尝试，并记录每个账号的 `attempted/succeeded/failed/empty`、耗时、原始数、日期内数和失败原因。
- 优先使用公开视频元数据中的标题、描述、发布时间、作者、视频链接和互动计数。
- 默认不下载音频、不做 ASR。若标题/描述不足以形成候选标题，可在总预算允许时对内容贫乏的高位候选做有限 OCR；OCR 不能成为入池门槛，最多处理 10 个候选，并有独立超时。

### 4.2 搜索关键词

核心关键词全部尝试：

1. `科技快讯`
2. `AI新品`
3. `大模型发布`
4. `开源大模型`
5. `芯片发布`
6. `人形机器人`

补充关键词按顺序执行，直到已聚类候选达到 20 条或全部完成：

1. `最新开源大模型`
2. `热门开源项目`
3. `GitHub热门项目`
4. `智能硬件新品`
5. `手机系统更新`
6. `游戏新作`
7. `游戏定档`

预算规则：

- 每个关键词最多保留 8 至 10 条有效公开元数据；具体值配置化，默认 10。
- 两条通道合计原始记录硬上限 100；到达后停止新增采集并继续处理已完成数据。
- 聚类事件输出硬上限 50。若超过，只按本合同热度规则截取前 50，并在报告中给出 overflow 数量；不得按真实性或有图与否截取。
- 关键词、顺序、单词预算、补充停止阈值、原始上限和事件上限必须放在版本化配置中，而不是散落硬编码。

## 5. 去重、聚类与排序

### 5.1 两层去重

1. 视频层：优先使用稳定视频 ID；缺少 ID 时使用规范化 URL 与作者/发布时间/标题指纹。一个视频只保留一条规范记录，来源命中列表合并。
2. 事件层：把描述同一新闻事件的视频合并为一条候选，但不得丢弃贡献视频。事件聚类必须保存 `aliases`、`contributing_videos` 和聚类依据/置信度。

聚类优先采用可测试的确定性规范化与实体/关键词相似度。确有必要时可做最多一次、批量、有限超时的大模型辅助规范化，但模型只能建议标题/聚类，不能核真、删除候选、计算热度或改变排序；模型失败必须回退确定性结果。

### 5.2 排序

排序输入只允许：

- 每条贡献视频的点赞、评论、收藏、分享等可得公开互动数据；
- 同一事件的独立视频数量；
- 不同已批准账号数量；
- 账号通道与关键词通道的交叉命中；
- 目标日内的新鲜度。

排序必须：

- 使用确定性、版本化公式；缺失互动指标按明确默认值处理；
- 在 JSON 中输出总分、各分量、聚合互动数、视频数、账号覆盖数和来源通道；
- 稳定排序，同分时采用明确的发布时间/稳定 ID 次序；
- 不受事实状态、图片成功、LLM 文案或人工偏好影响。

## 6. Top 3 图片策略

- 必须先完成候选聚类和最终排序，再仅对 rank 1 至 3 执行图片获取。
- 每条最多 1 张主图和 1 张真正不同的备用图；全包最多 6 张。
- 每条图片阶段最多 300 秒，整个图片阶段目标 900 秒；超过预算立即保留已有成果并继续发布。
- 仍执行已有图片安全与相关性门：可解码、MIME 一致、非超长图、非整版、非明显无关拼图、非社交/抖音视频截图、主体与候选一致。允许官方网站、发布会现场、产品图、游戏封面/实机图及可靠媒体的正常配图。
- 图片判断只判断“是否适合作为该候选的画面素材”，不等同于核验新闻事实。
- Top 3 全部记录 `attempted/succeeded/failed/timed_out` 和原因；找不到合格图片不删除候选、不改变名次。
- rank 4 及以后不得触发图片搜索、下载或模型视觉判断。

## 7. 一小时执行预算与降级

全链路硬截止：启动后 3600 秒。目标完成时间不超过 2700 秒。阶段软预算：

| 阶段 | 软预算 |
| --- | ---: |
| 已批准账号采集 | 720 秒 |
| 核心关键词搜索 | 900 秒 |
| 补充关键词搜索 | 480 秒 |
| 日期过滤、去重、聚类 | 420 秒 |
| 排序 | 180 秒 |
| Top 3 图片获取 | 900 秒 |
| 发布与完整性验证 | 300 秒 |

阶段软预算允许共享未使用时间，但全局 3600 秒不可突破。所有网络、浏览器、模型、OCR 和子进程操作必须有有限超时并接受全局剩余预算。

降级顺序：

1. 停止尚未开始的补充关键词；
2. 停止可选 OCR/模型辅助，使用元数据和确定性聚类；
3. 停止获取备用图；
4. 停止余下图片请求；
5. 使用已完成候选发布 `partial` 包，明确缺失来源、未完成阶段和截止原因。

不得因为超时丢弃已经完成的候选或等待无限期。浏览器会话应复用一个项目实例，任务结束后按现有规则关闭，不能遗留一批窗口。

继续使用：

- 日期目录：`YYYY-MM-DD_每日素材`

每个包至少包含：

2. `candidate-pool.json`：完整机器可读事件列表与排序解释。
3. `raw-videos.json`：日期内规范化视频记录及命中通道/关键词；允许分层放置但必须进 manifest。
4. `run-report.json`：各阶段耗时、预算、来源/关键词尝试、排除/去重/聚类/overflow、图片尝试、错误和降级原因。
5. 现有兼容文件（如 `昨日热点素材简报.md`、`daily-material-pack.json`）可保留为 V2 视图，但不得继续表达“仅五条精选”或事实门槛。
6. 更新 OP 消费规则文档，使 OP 默认读取候选池，自行核验和选题；明确 copy_skill 只提供抖音热度与图片素材。

候选 JSON 最低字段：

- `event_id/story_id`、`rank`、`title`、`aliases`、`business_date`
- `published_at_min/max`、`source_lanes`、`matched_keywords`
- `contributing_videos[]`（视频 ID、标题、作者/账号、链接、发布时间、互动数据）
- `aggregate_interactions`、`video_count`、`account_count`
- `heat_score`、`score_components`、`clustering_basis/confidence`
- `truth_status: not_checked`、统一免责声明
- `image_status` 和可选图片清单

包状态：

- `success`：所有必需核心来源尝试完毕、候选处理与发布完成、未触发硬截止；不依赖事实确认或图片数量。
- `partial`：来源/关键词/后续阶段因失败或预算未完成，但已安全发布现有候选。
- `empty`：所有必需来源完整完成且目标日确实没有有效记录；必须发布可验证空包，不得伪造候选。

## 11. 测试方案

### 11.1 自动化测试

- 日期边界：北京时间零点、次日零点、时区和缺失发布时间。
- 关键词：核心全尝试、补充自适应停止、每词上限、全局 100 上限。
- 来源：所有已批准账号被尝试，candidate 账号不被生产采集。
- 去重/聚类：重复视频合并、同事件多视频聚类、贡献记录不丢失、不同事件不误合并。
- 排序：分数可解释、稳定；改变真伪/图片/LLM 字段不改变名次。
- 候选保留：未经证实、无图、单来源仍输出。
- 图片：仅 Top 3 调用；每条最多 2、全包最多 6；rank 4+ 零图片请求；视频截图等既有拒绝门继续有效。
- 预算：阶段超时、全局截止、取消和模型/OCR失败能发布 `partial`，不重复启动浏览器。
- 交换包：READY 最后写、指针原子更新、manifest/hash、日期消费、success/partial/empty、历史包不变。
- CLI/工作台：默认昨天、显式日期、无硬编码日期、中文状态与错误、任务后浏览器回收。
- 安全回归：secret 扫描、`third_party/MediaCrawler` 与 OpenMontage 未修改。

若涉及锁、worker、子进程或 Windows 进程判断，聚焦与全量 pytest 必须在隐藏的独立进程组中运行，禁止 `os.kill(pid, 0)`。

### 11.2 真实端到端验收

以 `business_date=2026-08-28` 运行一次真实、受控生产链，不能直接重放固定五条选择文件：

- 所有当前已启用、已批准 benchmark/trusted 账号都有尝试记录；候选池账号未被暗中启用。
- 6 个核心关键词全部尝试；若聚类候选未到 20，则继续补充关键词，直到达到停止条件或全部尝试。
- 输出不是固定 5 条精选包；本数据日目标至少 10 个非重复事件，理想 15 至 40。若真实来源确实不足 10，只有在报告完整证明所有必需来源已跑完时才能以 `partial/empty` 交付，不得伪造。
- 每个事件保留全部贡献视频和来源链接，排名/分数可追溯。
- Top 3 均有图片尝试记录，目标 3 条均有主图，最低 2 条成功才算本次真实验收通过；失败图不以视频截图或无关图凑数。
- rank 4+ 的图片网络请求数为 0；事实核验网络请求数为 0；大模型调用 0 或最多 1 次批量辅助，且不参与核真/排名/删除。
- `root_plus_business_date` 能从根目录和日期独立发现 READY 包，manifest/hash 校验通过。
- 真实墙钟时间小于 3600 秒，报告逐阶段耗时；目标小于 2700 秒。
- 结束后仅允许既有规则保留的一个项目浏览器，正常任务按配置关闭，不能留下重复窗口或孤儿进程。
