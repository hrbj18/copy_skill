# 单次开发指导文档：公开网络探索池与双通道热点交付

日期：2026-09-03  
状态：进行中  
工作目录：`D:\work\copy_skill`

## 一、问题、目标与已知边界

当前 V2.5 的公开事件读者通道只依赖 14 个受限来源和既有抖音发现结果。真实回放中，30 个公开事件里仅 7 条得到允许的文章详情，主榜仅有 3 条；这不是“主榜筛选过严”的证据，而是国际大厂动作、国内运营商/消费科技动作和突发 AI 安全议题没有被充分发现。

本轮建立一个**公开网络探索池**，与原始抖音热度池并列：

1. 使用有固定预算的“公司 × 动作 × 领域”查询矩阵，发现公开网页中的科技事件线索。
2. 记录每条线索的查询、URL、来源、页面日期、来源类别和发现时间；将搜索结果当作发现/归因，不把它们变成事实核验或虚构平台热度。
3. 将同一事件的公开网页线索与已有公开事件、抖音候选做可审计归并，保留原始抖音互动与排序不变。
4. 为 OP 交付两个明确不同的视图：详情门槛通过、面向普通读者的“每日科技热榜”，以及覆盖更广但带来源强度和状态的“全网选题候选池”。
5. 让“公开网络发现、抖音已传播、来源充足、仅单信源线索”可以区分，而不是将模型估计的关注度称为“热度”。

## 二、冻结范围与不做事项

- 修改仅限 `D:\work\copy_skill` 中的配置、项目自有 `src/`、测试、交接文档及当日生成物。
- 不修改 `third_party/MediaCrawler`、OpenMontage、浏览器配置、定时任务、Cookie、密钥或 `.env.local`；不读取本地凭据。
- 原始抖音视频、互动数、`heat_score`、`heat_rank`、`delivery_priority_score`、`delivery_rank` 与 `truth_status: not_checked` 绝不被公开网页结果重算或覆盖。
- 不将网页搜索排序、模型判断或单篇自媒体文章称为“真实热度”。没有抖音互动证据时，公开事件的 `observed_heat_status` 必须为 `unknown`。
- 不把“搜索结果有链接”视为事实已经确认。允许域名的文章详情只能按现有规则支持保守写作；社交帖、聚合页或单一弱来源仅作为候选线索，不能自动进入面向人的事实主榜。
- 不为了凑 20 条降低人读主榜的详情、受众路由、白话标题或事件动作层级门槛；不足时主榜保持 `partial`。
- 不接入需付费、需登录、无明确重试/超时边界的搜索 API。本轮优先使用现有 HTTP/RSS 基础设施及公开可读查询入口。

## 三、设计决策

### 3.1 查询矩阵与预算

配置一个可审计的矩阵，而非单一“AI 新闻”关键词：

- 公司动作：OpenAI、Anthropic、Google、Meta、NVIDIA、微软、苹果、腾讯、阿里、字节、百度、小米、华为、中国移动等，与“发布、上线、开源、升级、模型、安全、芯片、AI 设备、自动驾驶、监管”等组合。
- 主题动作：大模型发布/开源、AI 安全、芯片与算力、AI 消费硬件、机器人/汽车、重要政策与基础设施。
- 每条查询配置最大结果数、连接/读取超时、单次总预算与来源去重，失败写入审计而非阻断当日包。

查询时间窗口以目标日北京时间计算；结果中无法获得日期或明显超窗的记录保留审计但默认不升入交付候选。

### 3.2 证据、热度与候选状态

每个新网页线索都必须有 `public_web_discovery`，最少包含查询 ID/文本、结果 URL、来源域名、标题、结果摘要、结果时间、发现时间与来源类别。来源类别为：`first_party`、`reputable_media`、`search_or_aggregator`、`social_or_unverified`、`unknown`。

事件层记录：

- `discovery_channels`：`public_web_search`、`douyin_attention` 等；
- `source_strength`：详情数、来源类别计数、是否有第一方或允许详情；
- `observed_heat_status`：只有原始抖音互动可得时才为 `douyin_observed`，其他情况为 `unknown`；
- `candidate_status`：`detail_backed`、`lead_only`、`needs_more_sources` 或既有分流状态。

模型可做标题归一和同事件候选建议，但不能创造 URL、日期、来源、互动数、事实或热度。无法可靠归并时，宁可保留可审计的独立线索。

### 3.3 双视图交付与排序

1. `每日科技热榜.md`：只使用现有详情门槛、公众路由和白话表达通过的事件。它不显示链接、来源、处理语言或伪热度。
2. `全网选题候选池.md` 与 JSON：目标为至少 20 条**可审计候选**（若真实采集不足，诚实输出少于 20 条与原因），按独立 `selection_priority` 排列。其人读版简短写明“事件简述”和“线索状态”；机器版保留来源、来源强度、网页发现审计和是否有实际抖音热度。

`selection_priority` 可以综合来源强度、公司/事件影响、公众关联、时效和可理解度，但名称与字段不得使用 `heat`。有真实抖音互动的候选可额外保留 `douyin_attention_rank`，不与网页发现量混算。

### 3.4 异常与兼容性

- 网络、RSS、解析或模型失败必须有限时，并逐查询写出错误；已有日包可以复用允许的原始缓存，但须标记复用链。
- 旧包与缺少公开网页字段的记录可继续读取，默认其 `discovery_channels` 为空、`observed_heat_status` 不可知；不能因缺字段崩溃或被误写为已核验。
- 发布保护继续禁止同日 `success` 指针降级为 `partial`；候选池增长不能绕过该闸门。

## 四、实施任务

1. 定位现有公开事件搜索、详情、聚合、包导出和测试入口，确认可复用的 HTTP/RSS 限制与当前数据合同。
2. 扩展配置与校验，加入固定查询矩阵、公开查询源、每查询/每日预算和来源分类规则。
3. 实现有超时、去重、时间窗过滤和逐查询审计的公开网页发现适配器；接入事件去重和来源强度，不触碰抖音排序字段。
4. 实现候选状态、独立 `selection_priority` 与双视图导出；保留现有公众主榜准入规则。
5. 增加离线夹具/单元与集成回归：日期过滤、同事件合并、社交单信源降级、无抖音热度标识、主榜闸门、候选 Markdown 的可读性及旧包兼容。
6. 运行配置校验、聚焦测试、完整 pytest、编译检查、CLI doctor、有限真实目标日回放和包 inspect；检查网络失败/不足时没有假装得到 20 条或将旧包写成新采集结果。
7. 更新当前 handoff、运行 audit，并只追加本轮实际结果到过程记录。

## 五、验收标准

1. 配置中存在可审计的多主题查询矩阵和有限预算；单一“AI 新闻”关键词不再是唯一公开发现来源。
2. 每个公开网页候选在 JSON 中能追溯到查询、URL、域名、发现时间和来源类别；搜索/社交线索不会自动成为事实详情或真实热度。
3. 公开网页候选的 `observed_heat_status` 为 `unknown`，除非同事件存在原始抖音互动证据；原始抖音热度和排序字段的回归断言保持不变。
4. 同一事件的多个网页线索会合并并保留全部来源；不确定合并不丢失线索。单一弱来源会标为 `lead_only` 或 `needs_more_sources`。
5. 生成 `全网选题候选池.md` 和机器 JSON，尝试覆盖至少 20 条；真实不足时，文档明确显示实际数量和原因，不填充无关、过期或虚构事件。
6. `每日科技热榜.md` 仍只含详情支持、公众路由和白话表达合格的事件，查询源扩容不能降低 V2.5 的主榜准入规则。
7. 配置校验、聚焦测试、完整 pytest、`compileall`、CLI doctor、有限真实运行、产物 inspect 与 handoff audit 都通过；所有真实网络/模型限制都如实记录为 `partial` 或相应状态。
