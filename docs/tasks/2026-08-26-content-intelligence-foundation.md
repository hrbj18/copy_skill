## 1. 背景与目标

本项目不再从零实现抖音页面自动化。它应成为 OpenMontage 上游的独立“内容情报供应层”：持续观察对标账号、抖音公开热点和科技关键词内容，筛选高价值题材，并在 OpenMontage 每日 03:00 生产上一自然日科技快报之前，输出可机器读取的候选素材。

长期内容范围不仅包括每日科技新闻，还应能扩展到科技软件、科技硬件、开源项目、大模型更新、有趣的新科技产品和非当日但具有持续价值的科技分享。

本次任务目标是建立可继续开发的可靠底座，而不是一次性完成无人值守生产全链路。

## 2. 已冻结的技术决策

1. 采用 MediaCrawler 作为第一阶段开源采集底座，部署在本项目内部并与自有代码隔离。
2. MediaCrawler 负责抖音指定创作者主页、关键词搜索、登录态缓存和底层数据采集；不复制其内部实现到自有模块。
3. 自有 Skill 只负责配置、调用编排、数据标准化、热度评分、去重、状态诊断和 OpenMontage 数据合同输出。
4. 认证优先复用专用 Chrome 持久化登录态；登录失效时允许用户每两三天扫码或更新一次 Cookie，不追求永久免认证。
5. Codex 中转站大模型只用于题材分类、聚类、摘要和价值判断，不用于绕过登录、签名、验证码或平台风控。
6. OpenMontage 仍是事实核验、稿件生成和视频生产者。抖音标题与口播只能作为线索和热度信号，不自动成为新闻事实证据。
7. 本次不修改 `D:\codex_work\OpenMontage`，只验证输出兼容其现有快照合同。
8. TikTokDownloader、F2 和 Skyvern 本次不部署。它们保留为后续下载、游客态接口或浏览器异常恢复的候选组件，避免一次引入多个大型底座。

## 3. 本次开发交付范围

### 3.1 开源底座部署

- 将 MediaCrawler 固定到本次验证过的上游提交，放入 `third_party/MediaCrawler`。
- 安装其独立 Python/Node 依赖，不污染本项目自有运行时。
- 保存上游来源、提交、许可证和本地部署方式说明。
- 至少验证项目帮助入口或等价的无副作用启动入口可以运行。

### 3.2 可安装的 Codex Skill

创建 `skills/douyin-content-intelligence`，触发范围包括：

- 配置或检查抖音对标账号；
- 采集对标账号与关键词内容；
- 生成 OpenMontage 抖音热点/对标账号快照；
- 检查登录状态和采集环境；
- 对历史采集结果执行标准化、评分和去重；
- 诊断每日内容供应任务失败。

Skill 不应在普通视频制作、通用新闻写作或不涉及内容情报供应时触发。

### 3.3 自有编排与标准化模块

建立一个轻量 Python 包与命令入口，至少支持：

- `doctor`：检查 Python、Node、Chrome、MediaCrawler、配置和目录状态；
- `normalize`：把 MediaCrawler 或测试夹具的不同字段映射为统一视频记录；
- `export-openmontage`：原子写出 OpenMontage 当前可消费的两个 JSON 快照；
- `run`：组合标准化、时间窗口、评分、去重和导出；默认仅使用已有采集文件，不静默发起浏览器登录或大模型付费调用。

### 3.4 配置与状态

- 对标账号和内容分类必须可配置，不能硬编码在代码中。
- 第一版预置三个已确认抖音号，但允许后续追加账号、关键词和类别。
- 密钥、Cookie 和浏览器凭据不得写入 Skill、日志、测试或版本化配置。
- 输出包含生成时间、目标日期、来源、账号、标题、互动数据、视频地址、发布时间、评分解释和稳定视频 ID。
- 保存去重状态，支持重复运行且不重复制造记录。

## 4. 数据架构

### 4.1 统一视频记录

最低字段：

```json
{
  "video_id": "稳定作品ID",
  "title": "视频标题或描述",
  "account_id": "账号稳定ID",
  "account_name": "账号名",
  "share_url": "作品链接",
  "published_at": "ISO-8601时间",
  "play_count": 0,
  "digg_count": 0,
  "comment_count": 0,
  "share_count": 0,
  "collect_count": 0,
  "category": "daily_news|ai_models|software_tools|hardware_products|open_source|interesting_tech|unclassified",
  "source": "douyin_creator|douyin_search|douyin_hotboard",
  "score": 0.0,
  "score_reasons": []
}
```

### 4.2 OpenMontage 兼容输出

输出目录默认为本项目 `output/openmontage/<目标日期>/`，包含：

- `hotboard.json`：`captured_at` + `items[]`，兼容 `word/hotScore/url`；
- `benchmark_accounts.json`：`captured_at` + `videos[]`，兼容 `title/account_name/play_count/share_url`；
- `content_candidates.json`：完整候选及评分，供后续扩展使用；
- `run_report.json`：输入、过滤、去重、输出数量和异常摘要。

只有在以后获得明确授权时，才把产物复制到 OpenMontage 的配置目录；本次仅做兼容验证。

## 5. 第一版评分与过滤

评分必须是确定性的，便于复验；大模型增强留到后续任务。

- 时效：发布时间越接近目标窗口末端越高；超过配置窗口的记录排除。
- 互动：点赞、评论、分享、收藏采用对数缩放，避免超大账号完全垄断。
- 账号内异常热度：有足够样本时，与该账号近期中位数比较。
- 题材匹配：配置关键词命中提供可解释加分。
- 数据质量：缺少标题、稳定 ID、链接或时间时降级或排除。
- 去重：优先按作品 ID，其次按规范化链接和标题指纹。

不得把播放量缺失自动解释为零价值；缺失字段要在评分原因和运行报告中明确表示。

## 6. 认证、稳定性与合规边界

- 使用专用 Chrome 用户目录或 CDP 复用登录态，不操控用户日常工作的 Chrome 窗口。
- 不自动解决验证码，不实施隐匿式绕过；遇到登录/验证挑战时保存明确状态并停止该来源。
- Cookie 只允许保存在被忽略的本地 secrets 或浏览器配置中。
- MediaCrawler 的 README 含“仅供学习参考、禁止商业用途”的声明。本次部署视为内部技术验证；在商业化、再分发或公开托管前，必须重新确认上游许可和平台规则，必要时替换底座。
- 采集失败不得破坏上一次成功产物；正式输出使用临时文件后原子替换。

## 7. 测试与验收标准

### 7.1 部署验收

- MediaCrawler 固定提交可追溯；依赖环境可复现。
- 无副作用帮助或配置检查命令成功。
- 自有 `doctor` 能清楚报告可用、缺失和需人工处理项。

### 7.2 功能验收

- 至少使用三种不同 MediaCrawler 风格字段夹具验证标准化。
- 时间窗口、字段缺失、数值字符串、重复作品和标题重复均有测试。
- 评分结果确定、可解释，重复运行结果一致。
- OpenMontage 两个快照能被其现有 `collect_douyin_sources` 读取，并且只成为热度信号。
- 输出写入失败时不破坏已有文件。

### 7.3 Skill 验收

- 通过 `skill-creator` 的 `quick_validate.py`。
- `SKILL.md` 能正确区分配置、采集、导出、诊断四种任务。
- 支持资料按需读取，不要求后续 Agent 阅读项目历史流水账。
